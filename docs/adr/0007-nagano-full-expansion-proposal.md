# ADR 0007: 長野県全市町村への拡張（提案・未承認）

- ステータス: 提案（2026-09-10）。実装はまだ。人間の承認を待つ

## 背景
現在は長野県の 5 市を手動で `data/sources/nagano.yaml` に登録している。長野県には 77 市町村（19 市・23 町・35 村）
があり、全域に広げたい。人間の作業は最小にし、「自治体または自治体の移住推進組織が運営主体と明記されたサイトだけ巡回する」
という規約（ADR 0001）を自動で守れる仕組みにする。

## 1. 自治体の公式ドメイン一覧の入手元
- **市町村の名簿**: 総務省「全国地方公共団体コード」（JIS X 0402、政府標準利用規約 2.0＝ホワイトリスト適合）を一次情報にする。
  77 市町村のコードと名称が確定する。CSV を `data/reference/lg_codes_nagano.csv` として取得日付きで保存する。
- **公式 URL**: コード表に URL は無い。日本の自治体はほぼ `*.lg.jp`（`city.X.nagano.jp` / `town.X.nagano.jp` /
  `vill.X.nagano.jp` / `X.lg.jp`）を使う。`.lg.jp` は地方公共団体専用ドメインで、**ドメインの種別自体が公式の強い根拠**になる。
  解決手順: (a) lg.jp の命名規則から候補 URL を生成して到達性を確認、(b) だめなら「<市町村名> 公式サイト」の制約付き
  ウェブ検索で `.lg.jp` ドメインを拾う、(c) それでも不確実なら人間レビュー（論点 4）へ。
- Wikidata の公式サイト項目は発見のヒントにのみ使い、公開データとしては転載しない（CC BY-SA でホワイトリスト外）。

## 2. 空き家バンクページの自動発見と分類
- 発見は既存の `sitemill discover` を使う（公式サイトと sitemap を「空き家/空家/移住」等で走査）。lg.jp 公式サイトを起点にする。
- 各候補ページを次の 4 種に**自動分類**する（sitemill の共通モジュールとして実装）:
  - **第三者プラットフォーム**: ホストが既知の民間 ASP 一覧（akiya-athome.jp、homes.co.jp/akiyabank、rakuen-akiya.jp、
    akiyabank-all.com、ハトマークサイト 等）に一致 → `policy: link_only`。
  - **JS 描画（SPA）**: 本文テキストが極端に短く、`<script>`/chunk CSS が多い、または `id="app"` と「enable JavaScript」を含む
    → 今フェーズは `link_only`（将来 JSON API の有無を調査。伊那市 ina-akiyabank.jp が該当、ADR 0001 追記）。
  - **一覧（listing_index）**: 静的 HTML に物件らしい繰り返し（「◯◯万円」が 3 件以上、物件番号/所在地/価格トークン、
    または 価格/所在地 見出しの表）→ `policy: crawl` の seed。
  - **詳細（listing_detail）**: 単一物件（物件番号 1・価格 1・敷地面積/延床面積 等のラベル）→ 一覧からの follow で辿る。
- 判定は複数シグナルの一致度で**確信度**を出す。曖昧な本文は LLM に種別だけを分類させて補助できるが、**巡回の可否は論点 3 の
  運営主体ゲートで最終決定**する（LLM 単独では巡回対象にしない）。

## 3. 運営主体の根拠を自動で記録する方法
- **lg.jp ドメイン**: ドメイン種別が根拠。`operator_evidence = {quote: "運営ドメイン <host>（.lg.jp、地方公共団体専用）",
  url, checked_on}`、`operator_kind: municipality`。人間の確認は不要。
- **非 lg.jp（移住推進組織など）**: 39ijyu.com・furusato-iiyama.net・iju-omachi.jp のような自治体関連サイトは、次のどちらかを
  自動で探して記録する。どちらも取れなければ `unknown` にして人間レビューへ回す。
  - **相互リンク検証**: 公式 lg.jp ページから当該サイトへ「空き家バンク」等のアンカーで**公式に案内されている**リンクがあれば、
    そのリンクを根拠として記録（最も強い自動シグナル）。`operator_kind: municipality`。
  - **本文の根拠句**: 「Copyright © X City」「事務局: X市◯◯課」「◯◯市移住交流推進課」等を正規表現／LLM で抽出し引用として記録。
    協議会等が主体なら `operator_kind: municipality_affiliated`。
- 記録は既存の `OperatorEvidence`（引用・URL・確認日）にそのまま入り、`/data/` ページに表示される。

## 4. 確信度が低い自治体だけ人間レビュー（人間の作業を最小に）
- 市町村ごとに**確信度スコア**を出す。要素: ドメイン種別（lg.jp＝高）、発見の確度（sitemap 一致＞URL 推測）、
  分類の一致度、運営主体の根拠の強さ（lg.jp／相互リンク＝高、本文正規表現のみ＝中、無し＝低）。
- **自動採用（crawl）**: 運営主体が lg.jp または lg.jp からの相互リンクで確認でき、かつ一覧/詳細として高確信で分類できた場合。人間不要。
- **人間レビューに回す**: 運営主体が unknown、根拠が本文正規表現のみで閾値未満、分類が曖昧（SPA か一覧か）、
  または非 lg.jp ホストで相互リンクが無い場合。
- **仕組み**: `discover` は候補を確信度・提案分類・根拠つきで `data/review/<pref>.yaml`（レビュー待ち行列）に書き出す。
  高確信のものは `sources/<pref>.yaml` に `policy: crawl` として自動昇格。低確信のものは `policy: pending`（絶対に巡回しない）
  のままレビュー行列に残し、理由を 1 行添えて人間に**承認/却下/URL 修正**のチェックリストとして提示する。
  `pending` を crawl/link_only とは別状態として持ち、lg.jp か人間承認のどちらか無しには巡回しない（規約を自動で担保）。
- 人間の作業は「低確信の十数件を眺めて承認/修正するだけ」に収まる。

## 5. 全市町村での初回巡回・抽出の概算費用と所要時間
- 前提（実測ベース）: 詳細ページ 1 件の抽出は入力 ~3.3k・出力 ~0.2k トークン ≒ **$0.004**、物件を多数並べる一覧ページは
  出力が大きく **$0.05〜0.06/ページ**（Haiku 4.5 一次 API 料金 $1/$5 per MTok）。
- 見積り: 77 市町村のうち空き家バンクを持つのは ~60、静的 HTML で巡回できるのは ~40（残りは SPA/PDF/第三者＝link_only、LLM 費用ゼロ）。
  巡回できる 1 市町村あたり ~1 一覧（$0.06）＋ ~20 詳細（$0.004×20＝$0.088）≒ **$0.15/市町村**。
  - **初回抽出コスト**: 約 40 市町村 × $0.15 ≒ **$6**、再試行・バッファ込みで **概算 $8〜15（約 1,200〜2,300 円）**。
  - **定常（日次）コスト**: 変化したページだけ再抽出するので **$0.2〜0.5/日** 程度。
  - **所要時間**: 巡回は約 40 ホスト × ~20 ページ × 3 秒間隔 ≒ **40 分**（現エンジンは source を逐次処理。ホストは別なので将来は
    並列化で短縮可）。抽出は ~1,000 呼び出し × 数秒 ≒ **1〜1.5 時間**。**初回は概算 1〜3 時間**、以降の日次は数分〜十数分。
  - **人間レビュー**: 低確信の ~15〜25 市町村 × 1〜2 分 ≒ **一度きり 30〜60 分**。

## 実装順序（提案）
1. `data/reference/` に総務省コード表を取り込むローダーと、lg.jp URL 解決 + 到達性チェック（sitemill 側）。
2. ページ分類器（一覧/詳細/SPA/第三者）と確信度スコア（sitemill 側の共通モジュール）。
3. 相互リンク検証と運営主体の自動記録。
4. レビュー待ち行列（`data/review/`）と自動昇格、`policy: pending` 状態の追加。
5. 長野県 77 市町村で discover を実行 → 高確信を自動採用、低確信を人間へ。承認後に初回 crawl→extract→build。

## 影響
- sitemill に汎用の「発見→分類→確信度→レビュー行列」を足すことで、japan-life-checklist / japan-open-today でも同じ拡張手順が使える。
- 巡回のホスト並列化は別 ADR で検討（現状は 1 source ずつ逐次）。
