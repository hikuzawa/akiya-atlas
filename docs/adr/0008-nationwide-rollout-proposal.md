# ADR 0008: 全国 47 都道府県への展開（提案）

- ステータス: 提案（2026-09-10）。長野県全域（ADR 0007）と横展開検証（沖縄・香川）を踏まえた計画。
  実装は承認後。並列化のエンジン実装は sitemill ADR 0013 に従う。

## 背景
長野県 77 市町村（ADR 0007）に続き、沖縄県・香川県で発見パイプラインを検証したところ、
Nagano 式の設計（総務省コード表 → 候補ドメイン推測 → 県公式一覧でフォールバック → ページ分類
→ 運営主体ゲート → 自動採用/リンクのみ）はそのまま通用した。差は「ドメインの命名傾向」と
「静的に巡回できる空き家バンクの割合」で、設計変更ではなく**データ（県一覧）とスケール**の問題。
全国 1,741 市町村へ広げる計画を定める。

## 1. 市町村名簿と公式 URL の入手（全国）
- **名簿**: 総務省「全国地方公共団体コード」を既に `data/reference/municipal_codes.csv` に取得済み。
  47 都道府県 1,741 市町村（東京 23 特別区を含み、政令市の行政区は除く）が確定している。
- **公式 URL**: 各都道府県の公的な「市町村リンク集」を一次情報に、コード→公式URLの対応表
  `data/reference/{slug}_official_urls.json` を作る（長野・沖縄・香川で確立した形式）。
  横展開検証で分かった命名傾向の違い:
  - Nagano: `city/town/vill.<名>.nagano.jp`（地理型）と `<名>.lg.jp` が中心。候補推測がよく当たる。
  - Kagawa: 地理型と `lg.jp` が混在。東かがわ市は `higashikagawa.jp`（独自ドメイン）で推測は外れる。
  - Okinawa: `.okinawa.jp` が主で `.lg.jp` は少数。独自ドメイン（`nakijin.jp`・`chatan.jp`・
    `iejima.org/ieson/`）や www 無し・非ルートパスが多く、候補推測はほぼ外れ、県一覧が要になる。
  → **候補URL推測は「当たれば速い」最適化にとどめ、公式URLの正解源は県一覧とする**方針を全国で徹底する。
    県一覧の入手は 1 都道府県 1 ページの調査で、市町村ごとの調査は不要（横展開検証で 41/41・17/17 を取得）。

## 2. 発見・分類・運営主体ゲート（変更なし）
ADR 0007 の仕組みをそのまま使う。ページ分類（listing_index / detail / spa / third_party /
not_listing）と運営主体ゲート（lg.jp・地理型ドメイン・相互リンク）で、静的一覧だけを巡回対象に
自動採用し、登録制/JS/制度案内/第三者はリンクのみにする。第三者プラットフォーム一覧は sitemill の
設定で全国共通に持つ（サービス拡張可能）。

## 3. 人間レビューの最小化（原則の再確認）
人間に回すのは「AI が取れる情報をすべて取った後も運営主体を判定できない案件だけ」（ADR 0007）。
横展開検証でも、公式URLが県一覧で解決でき運営主体が確認できれば、分類に応じて自動決定できた。
全国でもこの原則を保ち、レビュー残が都道府県あたり目安 10 件を超えたら発見・判定側を見直す。

## 4. 並列化（sitemill ADR 0013 に準拠）
発見・巡回はホスト単位で独立なので、politeness（1 ホストあたりの間隔・robots）を保ったまま
ホスト並列化する。
- **全国初回バックフィル**: GitHub Actions の matrix で都道府県ごとに 1 ジョブ（最大 47 並列）。
  エンジン変更不要・失敗が県単位で隔離・再試行容易。各ジョブは自県の
  `data/sources/{slug}-auto.yaml` と `data/records/` だけを書く。
- **日次の増分**: sitemill のスレッドセーフ `PoliteClient` + ホストワーカープールで、1 ジョブが
  多数ホストの変化分を短時間で再取得する。
- どちらも「1 ホストあたりの間隔は縮めない」不変条件を守る（ADR 0003 / 0013）。

## 5. 段階的な展開順序
1. 近隣・小規模県で試す（既に長野・沖縄・香川で検証済み）。
2. 地方ブロック単位（例: 中部 → 中国四国 → 九州 …）で県一覧を用意し、matrix でバックフィル。
3. 各県ごとに discover→自動採用→crawl→extract→build を回し、レビュー残と実測費用を確認してから次へ。
4. 全県そろったら日次増分に切り替える。

## 6. 費用・時間・データ規模の見積り（横展開の実測ベース）

### 横展開検証（沖縄・香川）の実測（2026-09-10）
- **沖縄県 41 市町村**: 発見 16.8 分・299 リクエスト。自動採用 crawl=1（竹富町）・link_only=40・
  **pending=0**。公式URL解決は候補URL到達 37・県一覧が必要 4（今帰仁村 `nakijin.jp`、伊江村
  `iejima.org` 等）・未解決 0。状態内訳 available 1 / info 17 / none 22 / spa 1。
- **香川県 17 市町村**: 発見 8.0 分・132 リクエスト。link_only=16・**pending=0**。候補URL到達 16・
  県一覧が必要 1（東かがわ市 `higashikagawa.jp`）。当初 crawl 採用の 1 件（坂出市）は改修補助金の
  ページ誤採用だったため info に訂正。状態内訳 info 13 / none 4。
- **巡回・抽出**: 静的一覧を持つ 竹富町 で 5 件を抽出（坂出市は 0 件＝上記の誤採用）。LLM 費用
  **$0.014（約 2 円）**、時間は crawl 0.1 分 + extract 0.5 分。
- **link_only 3 件の実ページ再確認**（豊見城市・宜野湾市・宜野座村＝いずれも none）: 公式トップと
  「住まい」系サブページに空き家バンクの記載が無く、**「none（公式へリンク）」判定は妥当**だった。
- **設計の移植性**: Nagano 式（コード表→候補ドメイン→県一覧フォールバック→分類→運営主体ゲート）は
  そのまま通用し、両県とも pending 0。県差は「ドメイン命名（沖縄は `.okinawa.jp`・独自ドメインが多く
  候補推測が外れる→県一覧が要）」と「静的に巡回できる割合の低さ（沖縄 1/41、香川 0/17）」で、
  コード分岐は不要だった。

### 全国への外挿
- **発見**: 実測 約 0.4 分/市町村（沖縄 16.8/41、香川 8.0/17、長野 ~21/72）。全国 1,741 市町村で
  逐次 約 700 分（≒12 時間）。ホスト並列（ADR 0013）なら wall-clock は 1/8 程度に短縮できる。
- **巡回できる割合**: 横展開実測で crawlable は 沖縄 2%・香川 0%・長野 14%。加重で概ね **1 割弱**。
  全国 ~150 市町村が静的巡回対象と見込む。初回抽出費用 ≒ 150 × 約 $0.15/市町村（ADR 0007）
  ≒ **$23（約 3,500 円）**、再試行込みでも 1 万円未満。日次は変化分のみで **$0.2〜0.5/日**。
- **データ規模**: 長野+2県で 342 ページ。全国では市町村ページ 1,741＋物件ページで数千〜1 万規模。
  sitemap 分割・検索索引分割・増分ビルドが必要（次項）。

## 7. 全国規模で必要になる技術的手当て（この ADR の対象、実装は承認後）
- **sitemap 分割**: 単一 sitemap は 5 万 URL 上限。都道府県別 sitemap + sitemap index にする。
- **検索索引**: 全国の物件を 1 つの `search/index.json` に載せると重い。都道府県別に分割し、
  クライアントで必要分だけ取得する。
- **ビルドの増分化**: 変化した都道府県だけ再ビルドできるようにする（現状は全再生成）。
- **公開前チェック**（ADR 0012）はページ数が増えても効く。PII 検査・OGP・JSON-LD は据え置き。

## 8. GitHub Actions 無料枠（private 2,000 分/月）に収まるか

GitHub Actions は **ジョブごとの wall-clock 分を合算**して課金する（matrix の並列ジョブは合算され、
分数は減らない）。private リポジトリの無料枠は月 2,000 分。これを前提に見積もる。

| 用途 | 実行方式 | 月間の課金分 | 無料枠 2,000 分 |
|---|---|---|---|
| 初回発見（一度きり） | 逐次・単一ジョブ | 約 700〜1,300 分（1 回） | その月を圧迫 |
| 初回発見（一度きり） | ホスト並列・単一ジョブ | 約 100〜200 分（1 回） | 収まる |
| 初回発見（一度きり） | 県 matrix 47 ジョブ | 約 700〜1,300 分（合算・1 回） | その月を圧迫 |
| 日次パイプライン | **逐次**・単一ジョブ | 約 130 分/日 × 30 ≒ **3,900 分** | **超過** |
| 日次パイプライン | **ホスト並列**・単一ジョブ | 約 25〜40 分/日 × 30 ≒ **900〜1,200 分** | **収まる** |
| 日次パイプライン | 県 matrix 47 ジョブ | 47×（数分）× 30 ≒ 数千分 | 超過 |

**結論と構成（この ADR の決定）**:
- **日次パイプラインは「ホスト並列の単一ジョブ」にする**（ADR 0013 のスレッドセーフ `PoliteClient`
  ＋ホストワーカープール）。逐次だと月 3,900 分で超過するが、並列化で 1 ジョブ 25〜40 分に収まり、
  月 900〜1,200 分で **2,000 分の枠内**。matrix は課金分が合算されるため日次には使わない。
- **初回バックフィルは GitHub Actions で回さず、ローカル PC または Raspberry Pi で実行する**。
  理由: (1) 一度きりで 700〜1,300 分規模になり、実行した月の日次ぶんと合算すると 2,000 分を圧迫する。
  (2) 数時間の長時間ジョブは Actions の 1 ジョブ上限（6 時間）や失敗時の再試行コストに弱い。
  ローカル/RPi なら礼儀（ホスト間隔）を保ったまま夜間に流し、結果の `data/**` だけをコミットすれば、
  Actions の無料枠を一切消費しない。RPi は常時稼働・低消費電力で、`uv run sitemill run` をそのまま実行できる。
- コミットは `data/**` のみを対象にし、`checks.yml` は `paths-ignore: data/**` で回さない（ADR 0007、無料枠節約）。
  デプロイ（Cloudflare Pages）は Cloudflare 側のビルド枠で行い、Actions 分を使わない構成も選べる。

## 影響
- sitemill 側の必須変更は「ホスト並列 `PoliteClient`」（ADR 0013）のみ。sitemap 分割・索引分割・
  増分ビルドは全国規模で効いてくる generic 機能で、他サービスにも有用。
- akiya-atlas 側は都道府県ごとの `{slug}_official_urls.json` を足していくデータ作業が中心で、
  コードの分岐は増やさない（Nagano 式が全国で通用することを横展開検証で確認済み）。
