# ADR 0014: 一覧の密度とページの重さ

- ステータス: 採用（2026-09-15）
- 関連: ADR 0003（検索の軸とページ構成）、ADR 0005（視覚要素）、ADR 0012（県ごとの所有者向けページ）

## 背景

参照デザイン（Google Stitch）をもとに、物件・市町村・所有者向けの 3 ページを見直した。
参照案は「項目が埋まった物件」と「制度が数件の自治体」を前提に組まれていたが、実データは違った。

- 物件のスペック 6 項目のうち **0〜1 個しか取れていない物件が 65%**（3 項目以上は 9.8%）
- 補助制度は全国 **2,939 件 / 828 自治体**。県ページでは 1 ページに数百件
- 空き家バンクの窓口は北海道で **179 市町村**

この状態で参照案の見た目をそのまま作ると、空白の多いカードと、延々と続く一覧になる。

## 決定

### 1. 一覧は 1 行、カードは横スクロールのときだけ

市町村ページの物件一覧をカードから 1 行表示にした。375px で **3.5 件 → 9.3 件**が 1 画面に入る。
価格と地区名が縦に揃うので見比べられる。カードは「下半分が空く」形で、項目の少ない物件では
空白を並べているだけだった。

トップの「最近確認した物件」はカードのまま。横スクロールで数件を見せる場所で、密度の利点が無い。

状態（成約済・掲載終了の可能性・状況・補助制度あり）はバッジではなく meta 行に文字で入れる。
色だけに意味を持たせない方針とも合う。数値にできず原文のまま出す価格（「53,000円/月、礼金1ヶ月」）は
小さくし、見出しを次の行へ送る。切り詰めると意味が変わるので、原文は必ず全文を残す。

### 2. 「眺めるもの」は畳み、「探すもの」は畳まない

**補助制度は畳む**。各グループの先頭 5 件を開き、残りは `<details>` に入れる。制度は
「どんな制度があるか眺める」ものなので、先頭を見せれば足りる。見出しには必ず総件数を出す
（「空き家向けの補助制度 136件」）。畳んだ中身は HTML に残るので検索エンジンからは読める。

**窓口は畳まない**。所有者は「自分の市町村」を探しに来る索引なので、8 割を畳みの中に入れると
毎回開く操作が要る。代わりにカードをやめて名前だけの並びにした（179 件で 32,443px → 2,940px、
1 行に 3.6 件）。掲載物件のある市町村を件数つきで先に出し、残りは市町村コード順（おおむね地域順）。

判断の分かれ目は**そのページでの役割**で、件数ではない。

### 3. 全国ページに全件を集めない

`/owners/` は補助制度 2,939 件を、`/data/` は出典 1,741 件を 1 ページに並べていた。
どちらも県ごとのページへ送り、全国ページは件数と導線だけを持つ。

- `/owners/`: 件数（2,939 件 / 828 市町村）と種別の内訳、47 県への導線。**制度名は出さない**。
  全国から数件を選ぶ基準が作れないため、中途半端に見せるより出さない
- `/data/`: 出典一覧の目次。出典そのものは `/data/<県>/`（47 枚）に置く。
  信頼ブロックの「出典一覧」も、県が決まるページではその県の一覧へ送る

### 4. 信頼ブロックの出典は代表だけ

sitemill の検査（`build/trust.py`）が見るのは `data-sitemill-trust` の有無だけで、出典の列挙は
要求していない。全件を並べると県ページのフッターが 7,331px になり、本文（7,549px）と同じ大きさに
なっていた。**最近確認した 5 件＋出典一覧への導線**にする。代表を「最近確認した順」にするのは、
信頼シグナルの目的が「いつの情報か」を示すことだから。全件は `/data/<県>/` にあるので失われない。

## 表示の解決と転送量の解決は別

`<details>` は**表示を隠すだけで、HTML は配信される**。補助制度を畳んで県ページは読めるように
なったが、`/owners/` は 2,939 件ぶんの HTML を配ったうえで 10 件だけ見せる状態だった。
畳み込みは「長すぎる」への答えであって「重すぎる」への答えではない。

重さは**圧縮後で測る**。繰り返しの多い HTML は 6〜13% まで縮むので、生の大きさでは判断を誤る。

| ページ | 生 | gzip |
|---|---|---|
| `/owners/`（対応前） | 3,012KB | 322KB |
| `/data/`（対応前） | 2,184KB | 132KB |
| `/owners/hokkaido/`（畳み込み済み） | 251KB | **33KB** |
| 市町村ページ（最大／中央値） | 76KB | **10KB / 4KB** |

畳み込みを入れた 2 種別は、圧縮後で見れば問題が無かった。対応が要ったのは「全件を 1 ページに
集める」種別だけで、そこは畳むのではなく**載せない**ことで解いた。

### 手元の gzip で本番が予測できる

配置後に本番（Cloudflare）と突き合わせたところ、**手元の gzip と本番の brotli はほぼ一致した**。
大きいページほど brotli が有利になるが、差は 1KB 以内。**手元で gzip 後を見ておけば、
配置しなくても転送量を判断できる。**

| ページ | 手元 生 | 手元 gzip | 本番 br |
|---|---|---|---|
| 物件 | 15KB | 5KB | 5.0KB |
| 市町村 | 34KB | 7KB | 7.5KB |
| 所有者向け（県・北海道） | 251KB | 33KB | 30.9KB |
| トップ | 37KB | 7KB | 6.9KB |
| 出典（北海道） | 222KB | 16KB | 15.1KB |

### 計測そのものを疑う

ローカルで測るときは 2 つ落とし穴がある。どちらも 2026-09-15 に実際に踏んだ。

1. **Lighthouse のローカル計測は非圧縮**。`python -m http.server` は圧縮しないので、
   Lighthouse の「転送量」も CSS も索引もすべて生の大きさで出る。本番の判断に使うときは
   gzip 後へ換算する。これを忘れて「CSS 31KB は削る余地がある」「索引 61.6KB が最も重い」と
   二度誤った（実際は 8.1KB と 5.7KB）
2. **端末のウイルス対策ソフトが注入する**。この端末の Kaspersky が localhost の応答に
   198KB のスクリプトを差し込んでおり、それが LCP と実行時間を支配していた。1 回目の計測は
   「物件 83→78」と出たが、`--blocked-url-patterns="*kaspersky-labs.com*"` で落とすと
   100→100 になり、3 回とも同値（変動ゼロ）になった。**数字が動いたら、まず計測の前提を疑う**

## 影響

- ページ数 5,989 → 6,036（`/data/<県>/` が 47 枚）
- `/owners/` 322KB → 8KB、`/data/` 132KB → 5KB、北海道の県ページ 44,570px → 8,907px（55.7 → 11.1 画面）
- 再発防止のテスト: `test_national_pages_send_the_full_lists_to_prefecture_pages`。
  `/owners/` に制度名が出ないこと、`/data/` に出典が出ないことを見る。畳んで解決しようとすると落ちる
