# ADR 0016: 公開する直前に性質を確かめる。巡回をやめた情報源の物件は退役させる

- ステータス: 採用（2026-09-16）
- 関連: sitemill ADR 0024（守りたい性質は公開する直前に確かめる）、ADR 0010（広告掲載の検査）、
  ADR 0015（トップで公言している巡回数）

## 背景

japan-open-today で、CI のキャッシュが古い `assets.json` を復元してコミットし、直した写真が
翌晩に戻った（sitemill ADR 0024）。同じ形の事故が akiya-atlas で起きていないかを調べた。

### 調べて分かったこと

- **キャッシュは問題なかった。** `pipeline.yml` の `actions/cache` は `data/raw` と
  `data/llm_cache` だけで、どちらも git 管理外（追跡中のファイル 0 件）。LLM キャッシュのキーは
  提供元・モデル・プロンプト・入力本文・スキーマのハッシュなので、古い応答が新しいページに使われない
- **履歴に「値が A → B → A と戻った」箇所はあったが、どれもキャッシュによる戻しではなかった。**
  物件レコードの 181 件は、**全件で**戻った時点の抽出が `cached=false`（その時点で LLM を呼び
  直していた）。ページが変わって抽出し直したら、前と同じ文言や値になっただけ。キャッシュが戻したなら
  「ページは変わったのに `cached=true`」になるはずで、それは 0 件。補助制度の 41 件は同じ日の意図した
  再構成。`data/sources` の 135 行は、補助制度の収集が補助制度のページを巡回するために 651 市町村の
  `policy` を `link_only` → `crawl` にしたため（物件一覧のページが復活した市町村は 0、
  `bank_status` が変わった市町村も 0）
- **ただし、直した判断が本番に効いていない例が 2 件あった**（下の「失敗の経緯」）

## 失敗の経緯

**兵庫県小野市**: 2026-09-12 に「物件一覧が PDF だけで、読めた 1 件も信用できない」として巡回を
やめた（`municipal_overrides.json` に `link_only`）。ところが 9/11 に取り込んだ物件 `0135` が
`active` のまま残り、**9/16 まで詳細ページが公開され、サイトマップにも載っていた**。
市町村ページは「データ件数 0 件」と出していたので、見た目では気づけなかった。

**北海道遠別町**: 物件ページが巡回対象から外れた後も、9/14 に最後に見えた 1 件が同じく公開されていた。

### なぜ既存の歯止めで見えなかったか

1. **巡回をやめる判断は `data/sources` を書き換えるだけ**で、取り込み済みのレコードに触れない
2. `finalize` は `policy: crawl` の情報源しか見ておらず、`link_only` になった情報源のレコードは
   stale にもならなかった。stale になっても「掲載終了の可能性」の注記つきで公開は続く
3. 補助制度の収集が `link_only` の自治体を `crawl` に変えた（補助制度のページだけを巡回するため）。
   **`policy: crawl` は「物件を巡回している」の目印にならなくなった**
4. ビルドはレコードの `status` だけを見て物件ページを作る。どの経路で `active` のまま残ったかは
   問わない。だから、書き込む側で防ぐ前提では穴が塞がらない

## 決定

### 1. 公開する直前に、4 つの性質を確かめる（`akiya-atlas publish-check`）

`pipeline.yml` の広告掲載の検査の直後、配置の前に置く。1 つでも破れていれば配置しない。

| 性質 | 見るもの |
| --- | --- |
| 物件ページを巡回していない情報源の物件を、インデックスできる形で公開しない | データ（active / stale のレコード）と生成物（noindex でない物件ページ、サイトマップ） |
| 人が固定した扱い（`municipal_overrides.json`）が守られている | `link_only` の自治体は物件ページを巡回せず、物件ページも公開しない。`no_website` の自治体はページを持たない |
| 取り下げ依頼のパス（自身と配下）の物件ページを、インデックスできる形で公開しない | 生成物とサイトマップ |
| 公言している巡回数が正しい | トップの「全国 N 市町村の空き家バンクを毎日巡回」の N が `bank_status: available` の数と一致し、その全部が実際に物件ページを巡回している |

**導入の時点では、4 つのうち 2 つは通っていた**（取り下げ・巡回数）。通っているものも入れるのは、
将来ずれたときに気づくため。取り込み側で揃えていても、別の経路で崩れうる（sitemill ADR 0024）。

データだけで確かめられる分（1・2・4 の一部）は `tests/test_publish_check.py` でコミット済みの
データにも当てる。push のたびに気づける。

「物件ページを巡回しているか」は `policy` ではなく、**seed に `listing_index` か
`listing_detail` があるか**で判定する（`service.crawls_listings`）。上の経緯 3 のため。

### 2. 巡回をやめた情報源の物件は退役させる（`status: retired`）

`finalize` の最後、重複の判定の前に `retire_unlisted` を呼ぶ。

- 物件ページを巡回していない情報源の `active` / `stale` のレコードを `retired` にし、履歴に残す
- **削除はしない。** 巡回に戻したら、退役の後に取り込み直されていれば `active`、そうでなければ
  `stale` に戻す（`stale` は次に見えたときに `active` に戻る）
- `stale`（30 日見えない）とは分ける。`stale` は「掲載終了の可能性」の注記つきで公開を続けるが、
  `retired` は**公開しないと決めた**もの

### 3. 退役した物件の URL には、noindex の「掲載終了」ページを残す

一覧・検索・最近の物件からは外す。個別の URL は、**削除して 404 にせず**、noindex の短いページに
置き換える。

- 既に索引された URL から来た人を、市町村のページと自治体の一次情報へ送れる
- 本来は **410（Gone）** が正しいが、Cloudflare Pages の静的配信では返せない（`_redirects` は
  3xx と 200 だけ）。Pages Functions を足すほどの件数ではない
- noindex のページは **sitemill がサイトマップに出さない**（`build/site.py`）。検索結果からは
  次のクロールで外れる
- ページには物件の中身（価格・所在地・要約）を出さない。公開しないと決めたデータだから

## 影響

- 退役: 2 件（小野市 `0135`、遠別町 `1`）。サイトマップは 6,126 → 6,124 URL
- 公開前の検査は手元で 6 秒弱（uv の起動込み、6,132 ページ）。日次の所要時間にはほぼ影響しない。
  最初は情報源の YAML（全国分で 2 秒）を 6 回読み直して 17 秒かかっていたので、1 回だけ読む形にした
- `retired` はエンジン（sitemill の `RecordStore`）が知らない状態。`upsert` は `stale` だけを
  `active` に戻すので、`retired` を戻すのは `retire_unlisted` の役目になる

## 追記: 取り下げが隠しすぎていた（2026-09-17）

### 何が起きたか

2026-09-12 に、自治体から「当町の物件は成約済みのため取り下げを」という依頼が届いた。
**添えられた URL は県のページ `/nagano/`** だった。取り下げは「そのパス自身と配下」を隠す作りなので、
**長野県の掲載中の物件がすべて（ページとして 191 件、レコードとして 241 件）9/17 まで隠れていた**。
本番の長野県ページは「掲載物件が 0 件」を出していた。

### なぜ誰も気づかなかったか

1. **範囲を限る仕組みは書かれていたのに、使われていなかった。** `takedown.py` に物件ページと市町村
   ページの URL だけを受ける正規表現（`LISTING_PATH` / `MUNI_PATH`）が定義されていたが、どこからも
   呼ばれていなかった。しかも 6 桁のコードだけを想定していて、「コード-名前」の 5 市（東御・佐久・
   飯山・大町・伊那）を受けられなかった。そのまま配線していたら、今度はこの 5 市への依頼が黙って
   効かなくなるところだった
2. **取り下げは静かに効いた。** 取り込みのログは「非表示にするページ: 1 件 #1 /nagano/」と出すだけで、
   それで何ページが消えたかを出していなかった。「1 件」に見えた
3. **この ADR の最初の検査は「隠すべきものが出ていないか」しか見ていなかった。** 隠しすぎは見ておらず、
   導入の日に通っていた

### 決定

- **自動で効くのは、物件 1 件か市町村 1 つのページを指す依頼だけ。** 県・トップ・所有者向けなどの
  URL は隠さず、`takedowns.json` の `unscoped` に残して人の判断に回す。CI では `::warning::` にする
- 一覧を手で書き換えて範囲外のパスを `takedowns` に入れても、**読むときに効かせない**
- 取り込みのログに**依頼ごとの非表示ページ数**を出す（「取り下げ依頼 N 件により、掲載中の物件
  M ページを非表示」）。公開前の検査の要約にも出す
- 公開前の検査に**隠しすぎ**を足す。掲載中の物件でページが無いものは、物件か市町村を指す取り下げで
  説明できなければならない。**どの経路で消えたかは問わない**ので、取り下げ以外の原因で物件が消えても
  気づける。件数のしきい値は置かなかった。「1 つの依頼は 1 つの市町村より広く効かない」という
  構造の条件のほうが、正しい依頼を誤って止めない

### 影響

- 長野県の 191 ページが戻る。依頼者の物件も一時的に見える状態に戻るが、成約済みなら巡回で掲載終了の
  扱いになる（ユーザー判断、2026-09-17）。町が分かり次第、Issue の対象 URL をその町のページに直す
- ページ数 6,132 → 6,323、サイトマップ 6,124 → 6,315 URL
